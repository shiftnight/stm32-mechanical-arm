1项目全景：先建立一张地图

1.1 它到底是什么

一句话概括：一块 STM32F103C8 最小系统板，通过 6 路舵机驱动一条 4 自由度机械臂；上位机（电脑软件 / PS2 手柄）通过串口发文本指令，单片机解析后转换成 PWM 波形，让舵机转到指定角度。

把这句话拆成四个技术要素：

主控STM32F103C8T6
Cortex-M3 @ 72MHz，64KB Flash，20KB RAM
执行器6 路舵机
180° 位置伺服，20ms 周期 PWM 控制
通信USART1 + USART3
115200bps，文本指令协议
存储W25Q64 (8MB)
SPI 接口，掉电保存动作组与校准值

它不是：带闭环反馈的工业机械臂（没有编码器、没有力矩控制、没有轨迹插补）；它是典型的「开环示教型」玩具/教学机械臂——你先用手把姿态摆好，让软件记下来，之后重放这一串姿态。理解这一点，你就明白为什么整个工程的重心在「动作组的存储与回放」而不是「伺服控制算法」。

1.2 目录结构：分层架构的物理体现

工程采用经典的五层分层架构。分层的本质是「依赖单向」：上层可以调用下层，下层绝不能回头调用上层。这样换硬件（比如把舵机换成步进电机）只需要改底层，业务逻辑不动。

1.3 一次控制的完整数据流

上位机发一条 #001P1500T1000!，到 0 号舵机真的转过去，中间经过了 7 个环节。这条链路是理解整个工程的主线索，后面每一章都是在放大其中一环。

这张图里藏着一个关键设计思想

第 ③ 步解析完之后，代码并没有去拉 GPIO 让舵机转，而是把目标值写进一个数组就返回了。真正的「动」发生在第 ⑤ 步的定时器中断里。这种「生产者—消费者」分工带来两个好处：

1）主循环不会因为「等舵机转完」而卡住，可以同时响应按键、手柄、串口；
2）舵机的时序由硬件定时器保证，不受主循环里各种 Delay_ms() 影响——精度与业务解耦。

后面你会看到，几乎所有「为什么这么写」的答案，最终都指向这一点。

1.5 中断资源与优先级

整个工程有 4 个中断源同时工作。优先级不是随便填的，它决定了「谁能打断谁」。

中断触发频率抢占/子优先级干什么
SysTick1000 Hz（1ms）0 / 0（最高）毫秒计时 + 每 10ms 扫描按键
TIM2约 800 Hz（每 1.25ms）0 / 2生成 8 路舵机 PWM，绝不能被打断太久
USART1按需（每字节一次）1 / 0接收上位机指令
USART3按需1 / 2接收总线指令
注意这两个「0」

SysTick 和 TIM2 的抢占优先级都是 0，比串口（1）高。这是有意为之：PWM 波形一旦被串口中断拖延，脉冲宽度就会变，舵机会抖动。把它设为最高优先级，等于告诉 NVIC：「哪怕正在收串口数据，也要先让我把这一路 PWM 的高低电平翻完」。代价是串口接收可能偶尔延迟几微秒——对 115200bps（每位 8.7μs）来说仍在容忍范围内。

2基础夯实：这个工程用到的七个底层机制

这一章是「原理课」。如果你对 STM32 已经熟悉，可以跳到 2.2 看时钟树的代码印证，或者直接去第 3 章。但如果你曾经对着别人的工程「能跑但不知道为啥能跑」，请老实读完——后面所有章节都会引用这里的结论。

2.1 芯片与最小系统：程序从哪一行开始跑

很多人以为 main() 是起点。严格说不是。上电复位后的真实顺序是：

  1. 硬件取向量：Cortex-M3 复位时，从地址 0x08000000（Flash 起始）读第一个 32 位字作为栈顶地址，读第二个字作为 Reset_Handler 的地址。这两个值来自启动文件里的「中断向量表」。
  2. Reset_Handler（在 startup_stm32f10x_md.s 里）：先把 .data 段从 Flash 拷贝到 RAM（有初值的全局变量），再把 .bss 段清零（初值为 0 的全局变量），然后调用 SystemInit()，最后 BL main。
  3. SystemInit()（system_stm32f10x.c）：ST 官方提供的默认时钟初始化，会把时钟配到 72MHz 并设置 SystemCoreClock 变量。
  4. main()：终于轮到你写的代码。
为什么这件事重要

因为 main.c 第一行又调用了一次 rcc_init()，这和 SystemInit() 是重复的。工程里这么写是为了「不依赖库的默认行为」，属于保守做法，不算错误。但你要知道：如果哪天你把 rcc_init() 删掉，程序照样能跑——因为 SystemInit 已经配过了。这类「冗余但安全」的代码在工业项目里非常常见，读代码时要有能力判断它是「必要」还是「保险」。

2.2 时钟树：为什么每一行 RCC_xxxClockCmd(..., ENABLE) 都省不掉

STM32 有个反直觉的设定：外设默认是没有时钟的。没时钟 = 寄存器写不进去 = 代码「看起来执行了但毫无效果」。这是新手 90% 的「代码没错但不工作」的根源。

时钟树的作用是把 8MHz 的外部晶振「加工」成各路外设需要的高频时钟：

现在再看 rcc_init()，每一行就都对得上号了：

Hardware/rcc/h_rcc.c · 35-75 行rcc_init()：把时钟从 HSE 起步推到 72MHz

逐段说明：

  • RCC_DeInit()把 RCC 寄存器恢复默认值。好处是「不管你之前被谁改过什么，从干净状态开始」。代价是如果这段代码被重复调用（例如软复位后），前面的配置会丢——所以它只能出现在最开始的初始化里。
  • while (HSEStartUpStatus == ERROR)是一个死等循环。如果晶振虚焊或者起振电容不匹配，程序就永远卡在这里，表现为「上电毫无反应、LED 不闪」。调试时如果你怀疑时钟问题，第一件事就是量晶振是否起振（示波器看 8MHz 正弦/方波）。
  • RCC_HCLKConfig / PCLK1Config / PCLK2Config三次分频配置必须在 PLL 使能之前完成，否则一旦切换到 PLL 时钟，总线频率会瞬间超出外设承受范围。
  • while (RCC_GetSYSCLKSource() != 0x08)里的 0x08 是个「魔法数字」：RCC_CFGR 寄存器的 SWS[1:0] 位读到 10 表示「当前系统时钟源是 PLL」。库函数本可以用 RCC_SYSCLKSourceStatus_PLL 这个枚举，这里直接写了数值，属于偷懒写法，读的时候知道含义即可。
验证技巧

想知道时钟到底配没配对，在 main() 里加一句 UsartPrintf(USART_DEBUG, "clk=%d\r\n", SystemCoreClock);，串口应打印 clk=72000000。如果打印出 8000000，说明 PLL 没生效——而 SystemCoreClock 变量本身也依赖 system_stm32f10x.c 里的 SetSysClock()，这一层关系值得你自己追一遍。

「复用」到底复用什么

一个引脚内部有多路开关：一路接 GPIO 的输入/输出寄存器，其余几路接 USART、SPI、TIM 等外设。复用（Alternate Function）就是把开关拨到外设那一路。拨过去之后，你写 GPIO_SetBits() 是没用的——引脚由外设的硬件状态机控制。这就是为什么串口发送数据时，你只需要往 USART_DR 写一个字节，波形就会自动从 TX 引脚一位一位「流」出去，完全不占用 CPU。

2.4 中断与 NVIC：抢占优先级到底抢什么

中断的本质是「硬件事件强制改变 CPU 的执行流」。Cortex-M3 的 NVIC 支持两级优先级：

  • 抢占优先级（Preemption Priority）：数字越小越高。高抢占的中断可以打断正在执行的低抢占中断——这叫「中断嵌套」。
  • 子优先级（Sub Priority）：只在两个中断同时挂起时决定谁先执行；已经在执行的那个不会被子优先级高的打断。

本项目里 TIM2 是 0/2，USART1 是 1/0。所以：TIM2 可以打断 USART1 的中断服务函数，反之不行。为什么这么定？看第 8 章你会明白：TIM2 中断每次只做几十条指令就得退出，但它决定了 PWM 的脉宽精度，抖动几十微秒舵机就会「嗡嗡」抖。

中断服务函数的三条铁律

1）短：TIM2 中断每 1.25ms 就要进一次，函数里多一个 UsartPrintf() 就会崩掉时序；
2）不阻塞：不能在中断里 Delay_ms() 或者等某个标志；
3）清标志：进中断第一件事是 TIM_ClearITPendingBit() / 读 DR 清 RXNE，否则退出后立刻又进来，形成「中断风暴」，主循环被饿死。

2.5 定时器与 PWM：舵机到底要什么样的信号

这是全工程最值得先搞懂的一块，因为第 8 章的「手动生成 PWM」在别处几乎见不到。

舵机的控制原理

舵机内部是一个「比较器 + 电机 + 电位器」的闭环：它把输入信号的高电平宽度和电位器反馈的角度做比较，驱动电机转到两者相等为止。所以舵机只认「脉宽」，不认「占空比」，也不需要你告诉它转到哪一档速度。

本项目实际用的是 510~2490μs 而不是 500~2500μs

留了 10μs 余量。原因很实在：舵机机械行程到极限时会「顶死」，如果代码给了 2500μs 而机械上限在 2450μs，电机会持续堵转发热、烧毁。这 10μs 是软件限位的第一道保险，第二道是 servo_pwm_min[]/max[] 数组（见 7.3）。

为什么「定时器中断」能干「PWM」的活

STM32 的定时器有硬件 PWM 模式：配置好 ARR（周期）和 CCR（占空比），引脚就自动输出波形，CPU 完全不参与。但本项目没有用它，理由很硬：

  • 硬件 PWM 的通道绑死在特定引脚上（比如 TIM2_CH1 只能是 PA0），而这块板子的舵机接在 PB3/PB6/PB7/PB8/PB9/PB4 —— 东一个西一个，凑不出 6 个同一定时器的通道。
  • 换引脚就要重新布线 PCB，成本远高于「让 CPU 每 1.25ms 干一点点活」。

所以作者选择了「软件 PWM」：用一个定时器产生高频中断，每次中断翻转一路引脚，并把 ARR 改成「这一路还需要维持多久」。8 路 × 高低两段 = 16 次中断 = 一个 20ms 周期（50Hz）。第 8 章会把这段时序彻底推演一遍。

2.6 USART：一次能传几个字节，错了怎么发现

串口是异步通信：没有时钟线，双方靠「约定的波特率」各自计时。所以两边波特率必须一致，否则收到的全是乱码。

关键公式（h_usart.c 注释里也写了）：

USARTDIV = fCK / (16 × 波特率) = 72 000 000 / (16 × 115200) ≈ 39.0625

硬件会自动把 39.0625 拆成「整数部分 39 + 小数部分 1/16」。项目里配置的是 USART_WordLength_8b | USART_StopBits_1 | USART_Parity_No，也就是常说的 8-N-1——上位机软件里也必须选 8-N-1，否则收到的字符会错位。

一个本项目里真实存在的隐患

没有奇偶校验、也没有 CRC。如果一根线接触不良丢了半个字节，单片机会把残缺的字符串当成一条完整指令去解析——比如 #001P15 后丢了 00T1000!，解析器可能读到脉宽 15，然后因为限位保护被裁到 510。数据错了，但系统不会报错。工业场景里这就叫「静默错误」，比崩溃更危险。

2.7 SPI 与 W25Q64：为什么「写」比「读」麻烦十倍

SPI 是同步串行总线，有四根线：CS（片选）、CLK（时钟）、MOSI（主出从入）、MISO（主入从出）。相比串口，它有时钟线，所以可以跑到几十 MHz，而且天然全双工。

W25Q64 是 64Mbit = 8MB 的 NOR Flash。它有三个「反直觉」的限制，直接决定了 h_flash.c 里那些绕来绕去的代码：

物理限制后果对应代码
只能把 bit 从 1 写成 0想写 0xFF → 0x00 可以；想写 0x00 → 0xFF 必须擦除整个扇区（4KB）spi_flash_write() 里「先读整扇区 → 擦除 → 改数据 → 写回」
擦除最小单位是 4KB 扇区改 1 个字节也要擦 4096 字节，且擦除耗时约 45msrewrite_eeprom() 每次都整扇区重写

把这三点连起来，你就理解了「动作组为什么每个占 256 字节」

ACTION_SIZE = 256 不是凑巧，它正好等于一页。这样每个动作组都能独立地做一次页编程写完，不会跨页；同时地址计算极简：第 n 组的地址 = n × 256。这是一个「让硬件特性反推数据结构」的典型案例——好的嵌入式设计经常这样，先看外设的边界条件，再定数据格式。

本章小结（后面会反复用到）

① 外设不配时钟就是死的；② 复用模式引脚归外设管；③ 抢占优先级决定谁能打断谁；④ 舵机只认脉宽、周期要稳；⑤ 串口没校验，错了不会报；⑥ Flash 只能 1→0，改数据先擦扇区；⑦ 定时器中断是最可靠的「时间基准」。

3启动流程：main.c 的每一行都是一个决定

main.c 只有 178 行，但它是整个工程的「总装图」。初始化函数的调用顺序是有讲究的——顺序错了，硬件会以各种离奇的方式不工作，甚至烧舵机。

3.1 完整的 main() 与逐行解剖

User/main.c · 33-82 行main()：初始化 + 主循环

表面上是一串「初始化 + 死循环」。但其中有两段是需要重点理解的：for 循环预置 duoji_doing，以及 servo_init → TIM2_Init → Delay_ms(500) 这三步的严格顺序。我们一块一块拆。

① 为什么在初始化外设之前，先给 duoji_doing[] 填值

User/main.c · 43-49 行在一切硬件初始化之前，先把 8 路舵机的"当前值/目标值"都预置为 1500

这段代码看起来只是「赋初值」，实际是为了避免一个灾难：

如果不预设会怎样

duoji_doing 是全局变量，按 C 标准会被清零——所以 aim/cur/inc 全是 0。而 TIM2_IRQHandler() 会直接读 duoji_doing[i].cur 当脉宽用。cur = 0 意味着脉宽 0μs，也就是占空比 0% 的 PWM。多数舵机收到「完全没有脉冲」会进入失控状态，或者被误判为「最小脉宽 0°」，瞬间往一个方向猛转，把机械臂结构顶变形。

所以这 8 行赋值不是「给个默认值」，而是安全前提：让定时器一开始就输出合法波形（1500μs = 中位）。

顺带看一个细节：duoji_doing[i].time = 5000; 而 inc = 0。因为 cur == aim == 1500，差值为 0，inc = 0 表示「不需要移动」，time 暂时用不上。这三个字段的关系是第 7 章的核心，这里先有个印象。

② other_init()：从 Flash 恢复上次的姿态

这是整个工程里最「工程化」的一段代码，包含三层防御。先看全貌：

User/main.c · 106-178 行other_init()：读 Flash、校验、限幅、恢复位置

逐段拆解：

第一步：打开 Flash 电源引脚并延时 10ms。

spi_flash_on(1) 会把 PB13 从「LED 功能」切到「SPI2_CLK 功能」（第 12 章详述）。为什么之后要 Delay_ms(10)？因为 W25Q64 从上电/唤醒到能接受指令需要时间（数据手册里 tPUW 典型值 5ms），且 SPI 模式切换后第一帧容易丢。这类「看起来多余的延时」几乎都是芯片手册要求的，读代码时不要随手删。

第二步：读出整个配置结构体。

w25x_read((u8 *)(&eeprom_info), ...) 直接把一段 Flash 内容「盖」到结构体上：

Application/app_servo/app_servo.h · 47-67 行eeprom_info_t：掉电保存的"配置块"

注意 dj_bias_pwm[DJ_NUM + 1] 和 last_pos[DJ_NUM + 1] 都多留了一个元素（9 个而不是 8 个）。多出来那一个是校验位，专门存 FLAG_VERIFY = 0x25。这是没有文件系统时判断「这块 Flash 到底有没有被格式化过」的最便宜做法：

  • 新芯片擦除后全是 0xFF，读出来的校验位不是 0x25，于是走「初始化分支」；
  • 写过一次之后校验位变成 0x25，下次上电就知道「数据有效，可以用」。

第三步：三层限幅。

  1. version != FLAG_VERIFY → 整块配置作废，动作数量清零。
  2. 偏差值 dj_bias_pwm[i] 必须在 -500 ~ +500 之间，否则清零。500μs 相当于 67.5°，已经是很夸张的机械偏差了，超出这个范围说明数据被写坏了。
  3. 上次位置 last_pos[i] 必须落在该舵机的独立限位 [servo_pwm_min[i], servo_pwm_max[i]] 内才采用；否则保持 1500。特别注意 4 号舵机的范围是 833~2167（±90°），比其它舵机窄得多。

第四步：先定「当前位置」，再让舵机平滑归位。

User/main.c · 162-169 行用偏差算出初始目标，并调用 duoji_doing_set 让它"慢慢地"过去

这里出现了一个容易绕晕的点，值得单独讲清楚：

「防猛动」机制：为什么开机舵机不会抽搐

设想没有这套机制的原始实现：上电 → 舵机当前停在上次断电时的位置（比如 800μs）→ 程序把 aim 设为 1500 → 定时器立刻开始输出 1500μs 波形 → 舵机会以最大速度从 800 冲到 1500，机械冲击巨大，长期下来齿轮磨损、结构松动。

本工程的做法是分两步：

1）other_init() 里先把 cur 和 aim 都设成「上次保存的位置」（eeprom_info.last_pos[i]）。这样定时器启动后输出的波形，和舵机实际所在位置一致——舵机不动。
2）然后再调 duoji_doing_set(i, init_pos, 1000)，它会算出 inc = (目标-当前)/(1000/20)，让舵机用 1 秒的时间匀速走到目标位。

所以时序上必须保证：先写好 cur（第 2 步）→ 再配置引脚为输出（servo_init）→ 再启动 TIM2。这三步顺序反了，防猛动就失效了。

③ 那三段「看起来很随意」的语句

再看 main() 中间这几行：

  • u16 num = spi_flash_read_id(); + UsartPrintf：读 W25Q64 的 JEDEC ID 并打印。正常应打印 W25Q64 ID=ef16（ef 是 Winbond，16 是容量代号）。这是最快的外设自检手段：如果打印 ffff 或 0000，说明 SPI 接线/供电有问题，后面所有 Flash 操作都不用指望了。
  • servo_init()：把 6 个引脚配成推挽输出（内部有防猛动的「先置 ODR 再配模式」技巧，第 7 章讲）。
  • TIM2_Init(2000, 72 - 1)：启动 PWM 定时器。参数含义：预分频 71 → 计数频率 1MHz；ARR 初值 2000 → 每 2ms 进一次中断（后续中断里会动态改 ARR）。
  • Delay_ms(500)：等舵机稳定。这 500ms 期间定时器已经在输出波形了，舵机正按 duoji_doing_set(i, init_pos, 1000) 的节奏慢慢走。
  • set_kinematics(100.0f, 105.0f, 88.0f, 155.0f, &kinematics)：告诉逆运动学模块「这条臂的物理尺寸」。四个数字分别是底座高 100mm、大臂 105mm、小臂 88mm、爪子 155mm。这组数据必须和你的实物一致，否则算出来的坐标全是错的（第 11 章详解）。

3.2 SWJ_gpio_init()：为了多两个引脚，牺牲调试器

STM32F103 的 PB3、PB4、PA13、PA14、PA15 默认被 JTAG/SWD 调试口占用。而这块板子上，PB3 是舵机 0、PB4 是舵机 5，PA13/14/15 是 PS2 手柄的三根信号线——全撞上了。

GPIO_PinRemapConfig(GPIO_Remap_SWJ_Disable, ENABLE) 把整个 JTAG 和 SWD 全关掉，五个引脚全部释放。代价是：

重要副作用

关掉 SWD 之后，你就不能再用 ST-Link 在线调试或下载了（除非用 GPIO_Remap_SWJ_JTAGDisable 只关 JTAG 保留 SWD——但那样 PB3/PB4 依然能用，PA13/14 就保不住了）。

3.3 主循环：一个「前后台系统」的骨架

User/main.c · 73-82 行while(1) 里的六个任务

六个函数轮流调用，没有 RTOS、没有任务优先级、没有时间片。这种结构叫 前后台系统（Foreground/Background）：中断是「前台」（响应突发事件），主循环是「后台」（处理业务）。

任务函数阻塞吗职责
app_led_run()否（非阻塞计时）每 1s 翻转 LED，心跳指示
app_key_run()可能阻塞（按键里会Delay_ms）处理短按/长按事件
app_usart_run()否（查标志位）指令分发，是主循环里最重要的一环
loop_action()否（查时间差）动作组连播的推进器
app_ps2_run()否（50ms 节流）读手柄、映射命令
app_servo_save_pos_check()可能阻塞（写 Flash 约 50ms）每 30s 检查一次，位置变了就存 Flash
这个架构的「隐性代价」，你必须知道

前后台系统有个致命假设：每个任务都很快返回。一旦某个任务阻塞超过几十毫秒，其它任务全部延迟。本工程里有两个潜在的「长阻塞」：

1）app_key_run() 里短按会做「擦扇区 + 写字节 + 鸣叫 600ms」，总共可能阻塞近 700ms；
2）app_servo_save_pos_check() 里 rewrite_eeprom() 每次擦 4KB 扇区（约 45ms）+ 写 4KB，也会卡住主循环。

好消息是：舵机 PWM 在 TIM2 中断里，不受主循环阻塞影响，所以即使主循环卡 700ms，舵机依然在平滑运动。这就是「把关键时序放进中断」的价值——它让系统的最坏情况变得可接受。坏消息是：这 700ms 内串口收到的指令会因为 uart1_get_ok 丢弃（第 6 章）。

4时间基准：SysTick 与「不用 delay 的延时」

嵌入式里「时间」是个大问题。用 Delay_ms() 阻塞等待，会让 CPU 什么也干不了；用定时器做非阻塞计时，同样的功能就能和其它任务并行。本工程两种都用，而且用得挺讲究。

4.1 SysTick：Cortex-M3 自带的「心跳」

Hardware/timer/h_timer.c · 27-68 行SysTick 初始化、中断服务函数与 millis()

三个要点：

  1. SysTick_Config(SystemCoreClock / 1000)：这个库函数内部做了三件事——设置重装载值为 72000、清计数器、使能中断并启动。SystemCoreClock 是 72000000，除以 1000 就是 72000，即每 72000 个时钟周期中断一次 = 1ms。注意它依赖 SystemCoreClock 变量的正确性，如果时钟改了但没更新这个变量，所有延时都会按比例错。
  2. systick_us++：这不是微秒，是毫秒计数器（变量名有点误导）。它是全局时间基准，millis() 直接返回它。
  3. key_scan_times >= 10：每 10ms 扫一次按键。为什么不 1ms 扫一次？因为按键抖动通常持续 5~20ms，1ms 采样纯属浪费 CPU，而且更容易采到抖动中间态。
systick_us 是 u32，49.7 天溢出

这是所有用「毫秒计数器」的工程都会遇到的经典问题。0xFFFFFFFF ms ≈ 49.7 天。溢出回绕后，如果代码写的是 if (millis() > last + 1000)，就会永远不成立（因为 millis() 变成了很小的数）。

本工程统一写成 if (millis() - last > 1000)——无符号减法会自动处理回绕。这个写法值得记住，是嵌入式的基本功。

4.2 非阻塞延时的标准范式

看 app_led_run()，这是整个工程里「非阻塞」的教科书示例：

Application/app_gpio/app_gpio.c · 30-39 行每 1000ms 翻转一次 LED，不阻塞主循环

对比一下两种写法的差别：

阻塞写法（错误示范）非阻塞写法（本工程）
 
LED_TOGGLE;
Delay_ms(1000);
 
if (millis() - t < 1000) return;
t = millis();
LED_TOGGLE;
1 秒内 CPU 完全空转，串口指令收不到（中断能收，但主循环不处理），按键无响应1 秒内主循环跑了成千上万圈，其它任务照常执行

这个模式在工程里反复出现：app_ps2_run()（50ms）、app_servo_save_pos_check()（30s）、loop_action()（action_time）。看到 static u32 xxx_bak + millis() 的组合，就是在做节流。

为什么用 static？因为函数返回后局部变量会销毁，static 让它常驻内存，下次进来还记得上次的时间。这是 C 语言实现「状态记忆」最轻量的办法，不需要全局变量污染命名空间。

小细节：为什么 static u32 time_count = 0; 能正常工作

第一次调用时 millis() - 0 是一个很大的数（开机时间），必然大于 1000，所以立刻翻转一次。之后按 1s 节奏走。如果你想让它「上电先等 1 秒再开始闪」，就得把初值写成「当前 millis」。这种边界情况在小项目里无害，但移植到需要精确节奏的场合就要注意。

5GPIO 应用层：LED、蜂鸣器、按键与那个被复用的 PB13

这一章的对象都是「简单外设」，但里面藏着两个很典型的工程问题：按键消抖的状态机怎么设计，以及一个引脚被两个功能抢用怎么办。

5.1 LED：为什么「低电平点亮」

Hardware/LED.h · 8-31 行LED 引脚与四个操作宏

PB13 上的 LED 采用灌电流接法：LED 正极接 VCC（通过限流电阻），负极接 PB13。所以：

  • PB13 输出低电平 → LED 两端有压差 → 点亮；
  • PB13 输出高电平 → 两端都是 3.3V → 熄灭。

这种接法在 STM32 上很常见，因为 STM32 的引脚「灌电流（sink）能力」比「拉电流（source）能力」强，驱动 LED 更稳。代价是逻辑反了，读代码时看到 LED_ON() 实际是 GPIO_ResetBits() 千万别以为是笔误。

LED_TOGGLE 这个宏写得挺巧：1 - LED_GET_LEVEL()，读出当前电平取反再写回。注意它有副作用——宏展开后 GPIO_ReadOutputDataBit 会被求值两次吗？不会，因为整个表达式只出现一次。但如果有人写成 LED_TOGGLE; LED_TOGGLE; 连着两次，就会「翻两次 = 不变」。这类宏在调试时容易让人怀疑人生。

5.2 开机提示音：用「人」能感知的方式验证系统

Application/app_gpio/app_gpio.c · 45-57 行蜂鸣器 + LED 交替 3 次，作为开机自检信号

六个 Delay_ms() 加起来 600ms。这在实际产品里是「奢侈」的（用户会觉得开机慢），但在调试阶段非常有用：

  • 听到「嘀嘀嘀」三声 → 说明 rcc_init、SysTick_Init、app_gpio_init 都跑通了；
  • 完全没声音 → 卡在前面的初始化（最常见是 HSE 起振失败，卡在 rcc_init 的死等循环里）。

用「声/光」做分层自检是嵌入式的经典手法：不同的鸣叫次数对应不同的卡死位置。这个工程只用了 3 声「成功」，你完全可以把它扩展成「1 声 = 时钟 OK，2 声 = Flash OK，3 声 = 全部 OK」。

5.3 按键：一个 50ms 消抖 + 短按/长按的状态机

机械按键按下时，金属簧片会弹跳 5~20ms，产生一串高低电平抖动。如果直接读电平，按一次会被识别成好几次。软件消抖的标准做法是「连续 N 次采样都为低才算按下」。

本工程把扫描放在 SysTick 中断里（每 10ms 一次），逻辑写成一个隐式状态机：

Hardware/key/h_key.c · 59-128 行每 10ms 调用一次的按键扫描状态机

逐段拆：

  1. key1_press_time++ 的单位是「10ms」，不是「ms」。所以 DITHER_ELIMINATION_TIME 应该是 5（=50ms），LONG_PRESS_TIME 应该是 200（=2s）。读这类代码时一定要先确认计数单位，否则你会以为消抖时间是 50 个 10ms = 500ms。
  2. if (key1_flag == 0) 只在「还没确认按下」时累计；确认后 flag 变 1，就不再重复置位。这避免了每次扫描都刷新状态。
  3. if (key1_flag == 1) 在已确认按下的前提下继续看是否超过长按时间，一旦超过就 flag = 2 并立刻置 key1_pressing = 2——注意这里不等松开就动作了，所以长按会「按住即触发」。
  4. 松开分支里 if (key1_flag == 1) key1_pressing = 1;：只有「按下了但没到长按时间就松」才算短按。
  5. key1_flag = 0; key1_press_time = 0; 无论什么情况，松开就复位。这两行必须在最后，否则短按标志会被立刻清掉。
这个实现里有两个真实存在的小问题（读代码时要能看出来）

问题 1：长按会重复触发。 flag==2 之后，每 10ms 只要按键还按着，key1_pressing 就一直被赋值为 2。而 app_key_run() 里对 key1_pressing == 2 的处理是「打印一句话」，没有清零，所以串口会每 10ms 打印一次，刷屏。修法：长按触发后置 flag = 3（已处理），或者消费完就清零。

问题 2：key1_pressing 的清除职责不清。 短按分支里 key1_pressing = 0; 写了两次（中间隔着一个 app_setup_start()），而长按分支从不清零。这是典型的「状态变量没有单一清除点」，容易埋 bug。规范做法：主循环消费完事件立刻清零，中断/扫描只负责置位。

5.4 app_key_run()：按键干了什么「正经事」

Application/app_gpio/app_gpio.c · 67-112 行按键任务：KEY1 做 Flash 读写自检，KEY2 把 PB13 切回 LED

KEY1 短按做的事其实是个Flash 读写测试：读地址 0 → 值 +1 → 擦扇区 0 → 写回。它验证了 SPI 通信、扇区擦除、页编程三条链路。这类「按一下键跑一遍自检」的功能在开发板上很常见，比反复烧程序快得多。

但它同时暴露了一个设计问题：app_setup_start() 会阻塞 600ms，而它被放在主循环任务里调用——这 600ms 内串口、手柄、动作组全部停摆。真要改，应该改成「置一个标志，让 app_led_run 式的非阻塞状态机去鸣叫」。

5.5 PB13 复用：一个引脚，两种身份

这是本工程最值得学的一个「硬件妥协」。看原理图会发现：LED 接 PB13，而 W25Q64 的 SPI 时钟也接 PB13。一个引脚只能有一个功能，怎么办？

答案是分时复用：平时 PB13 当 LED 用；需要用 Flash 时，把它切成 SPI 时钟，用完再切回来。

Hardware/flash/h_flash.c · 40-61 行在「LED 输出」与「SPI2_CLK」之间来回切换 PB13

三个细节值得注意：

  1. GPIO_Init(GPIOB, &GPIO_InitStructure) 会重写 CRH 寄存器中 PB13 对应的 4 个位，其它引脚不受影响——所以可以放心地只改一个引脚。
  2. 切到 SPI 模式时先 GPIO_SetBits(GPIOB, GPIO_Pin_13) 再使能 SPI。这是为了让 CLK 线在空闲时保持高电平（SPI 模式 3 的 CPOL=1），否则从设备可能误判第一个边沿。
  3. spi_write_read(0xFF) 这个「空字节」不是多余的：它用来清空 SPI 移位寄存器里的残留数据，并且产生一个时钟脉冲让从设备的状态机同步。
这种设计付出的代价

每次读写 Flash 前后都要切换引脚模式（约几微秒），而且切换期间 LED 会「闪一下」——所以你可能会看到 LED 在保存动作时有不规律的闪烁。更重要的是：不能在中断里调用 Flash 操作，因为切引脚是全局状态，如果主循环正在用 SPI，中断里一插进来切走，数据就崩了。这就是为什么 spi_flash_on() 只在主循环路径上被调用，中断服务函数里从不碰 Flash。

如果重画 PCB，把 LED 挪到别的引脚（比如 PB0）就能彻底消除这个约束。但在不改硬件的前提下，分时复用是唯一解——识别「这是硬件限制导致的软件复杂度」，是读别人代码时最重要的判断力之一。

6串口与指令协议：整个系统的「入口」

这一章是全工程第二重要的部分（第一是 PWM）。因为上位机、PS2 手柄、动作组回放，最终都汇入同一个入口：uart_receive_buf。

6.1 Usart1_init()：五步初始化，顺序不能乱

这五步是 STM32 所有外设初始化的通用套路，记住它你就能自己看手册配任何外设：

6.2 发送：TXE 和 TC 到底该等哪个

Hardware/usart/h_usart.c · 245-276 行发一个字节 + 发字符串

uart_send_byte() 等的是 TXE（发送数据寄存器空）。含义是：「我刚写进 DR 的那个字节，已经被搬到移位寄存器了，DR 可以再收下一个字节」。

而 UsartPrintf() 里等的是 TC（发送完成）：

Hardware/usart/h_usart.c · 318-334 行UsartPrintf：可变参数格式化后逐字节发送，等 TC 而不是 TXE

两者差一个字节的时间（86.8μs @115200）。什么时候必须等 TC？ 当你发完数据要立刻做「依赖发送完成」的操作时——比如 RS485 收发切换、进入低功耗、或者软复位前保证最后一句话发出去。soft_reset() 里就调了 UsartPrintf(USART1, "stm32f103x6 reset") 然后立刻 NVIC_SystemReset()，如果等的是 TXE，最后几个字节可能还没发出去芯片就复位了。

还有一个 fputc 重定向

h_usart.c 末尾重写了 fputc()，让标准库 printf() 输出到 USART1。工程里其实两种都用：UsartPrintf()（自己实现，可控）和 printf()（方便但体积大）。用 printf 需要在 Keil 里勾选 Use MicroLIB，否则链接会报错或卡死。建议统一用 UsartPrintf，避免依赖编译器选项。

6.3 中断接收：一个 5 状态的「帧边界识别器」

串口是字节流，没有「包」的概念。要在字节流里切分出一条条指令，必须自己定协议。本工程的协议非常简洁——用首字符区分模式，用尾字符界定结束：

模式起始符结束符用途例子
1$!系统命令（停止/复位/执行动作组）$DGS:3!
2#!单舵机控制#001P1500T1000!
3{!多舵机一次下发{#000P1500T1000!#001P2000T1000!}
4<>动作组存储（写 Flash）<G0005#000P1500T1000!>

现在看中断服务函数怎么实现这个「帧边界识别」：

Hardware/usart/h_usart.c · 405-469 行USART1 接收中断：识别帧头帧尾，凑齐一条指令

逐段解剖：

  1. static u16 buf_index = 0; 用 static 是必须的——中断函数每次进来都是「同一次调用」，局部静态变量才能跨中断保持写指针。如果写成普通局部变量，每次进中断都会从 0 开始，永远只能存 1 个字节。
  2. sbuf_bak == '<' 这个判断放在 mode 判断之外，是个有意为之的特例。原因：<...> 存储指令可能在任何时刻到来（比如上位机正在发多舵机指令的中途），作者希望它能强行打断当前接收，立刻开始一条新的存储指令。这是一个「优先级更高的帧类型」的设计。
  3. if (uart1_get_ok) return; 这是丢包式流控：上一条还没被主循环处理完，新来的字节直接扔掉。好处是绝不会覆盖正在处理的指令；坏处是会丢包（6.5 节细讲）。
  4. uart_receive_buf[buf_index] = '\0'; 收完尾字符后补字符串结束符，这样后续 strlen / strstr / sscanf 才能安全工作。这一步极容易被忘，忘了就会出现「字符串后面跟着上次的垃圾数据」的诡异 bug。
  5. if (buf_index >= UART_BUF_SIZE) buf_index = 0; 溢出保护。注意它不是「丢弃多余数据」，而是「回到开头继续写」——所以超长指令会把缓冲区开头的字节覆盖掉，产生一条被拼接的畸形指令。这是本实现的一个真实缺陷（见 6.5）。
USART1 和 USART3 共用同一个缓冲区

两个中断服务函数都往 uart_receive_buf 里写，共用 uart1_get_ok 和 uart1_mode。这意味着两个串口不能同时收指令：如果 USART3 正在收一条长指令，此时 USART1 来数据，就会被 if (uart1_get_ok) return; 丢掉，或者更糟——两边的字节拼进同一个缓冲区，产生一条既不像 A 也不像 B 的畸形指令。

工程里之所以没出问题，是因为实际使用中同一时刻只有一个上位机在发。但如果接到「视觉模块 + 手柄」双输入的场景，就必须改成「每串口一个缓冲区」。这是一个典型的「当前需求下够用，扩展时会炸」的设计。

6.4 指令分发：app_usart_run()

Application/app_usart/app_usart.c · 48-78 行主循环里检测标志、按模式分发、最后清标志

这是主循环与中断之间的「交接点」，写法非常标准：

  • 先处理后清零：uart1_mode = 0; uart1_get_ok = 0; 放在最末尾。如果放在开头，处理过程中新到的字节会混进来。
  • 回显：UsartPrintf(USART_DEBUG, "%s\r\n", uart_receive_buf) 把收到的指令原样打回去。调试时极其有用（能确认到底收到了什么），但正式产品里应该关掉——它会占用发送时间，且在 115200 下每回显 20 字节就要 1.7ms。
  • 两个模式共用一个解析器：模式 2（#...）和模式 3（{...}）都调 parse_action()。因为 parse_action 内部是个「遇到 # 就解析一组」的循环，天然支持一条指令里有多个 #——所以单舵机和多舵机可以用同一段代码，这是第 9 章要讲的巧妙之处。

6.5 这个接收机制的三个缺陷（以及怎么改）

作为学习者，光看懂「它怎么工作」不够，还要能判断「它什么时候会坏」。这个接收机制有三个已知弱点：

缺陷 1：丢包无提示

if (uart1_get_ok) return; 意味着：主循环忙的时候（比如正在擦 Flash 的 45ms 里），上位机发的指令会被静默丢弃。用户看到的现象是「偶尔发指令没反应」，而且没有任何错误提示。

缺陷 2：溢出处理会造出畸形指令

if (buf_index >= UART_BUF_SIZE) buf_index = 0; 应改成「丢弃后续字节直到遇到结束符」：

if (buf_index >= UART_BUF_SIZE - 1) {
    uart1_mode = 5;        /* 新增"溢出丢弃"状态 */
    buf_index = UART_BUF_SIZE - 1;
}
/* 收到结束符时若处于溢出态，直接复位，不置 ok 标志 */

缺陷 3：没有超时复位

如果上位机发到一半断线（比如只发了 #001P15 就没了），uart1_mode 会一直停在 2，buf_index 停在 8。下一条指令来的时候，会接着往后拼——#001P15 + #002P1500T1000! → 变成一条乱掉的指令。修法是加一个字节间超时：在 SysTick 里记「上次收到字节的 millis」，超过 20ms 没新字节就强制复位 mode = 0; buf_index = 0;。

如果要认真重构，标准方案是「环形缓冲区 + 帧解析状态机」

中断只负责把字节塞进 ring_buf[256]（头指针 + 尾指针，不判断内容），主循环慢慢取出来解析。好处：① 中断里只做 3 条指令，极快；② 不丢包（只要缓冲区不溢出）；③ 双串口可以各有各的环。代价是多 256 字节 RAM 和一点代码量——对 20KB RAM 的 F103C8 完全负担得起。

这个工程没用环形缓冲，是因为它是「示教型」应用：指令是人手动一条条发的，速度慢、间隔大。 判断「要不要重构」的标准永远是实际负载，而不是「哪种写法更高级」。

7舵机驱动：如何让 6 个舵机「匀速、安全、不抖」地动

舵机驱动看似简单——给个脉宽就转。但要同时做到匀速（不猛冲）、限位（不撞结构）、不抖（波形稳定），需要一套中间数据结构。这一章讲的就是这个结构。

7.1 核心数据结构：servo_t 的四个字段

Hardware/servo/h_servo.h · 82-95 行servo_t：每路舵机的完整状态

四个字段各司其职，缺一不可：

字段类型含义为什么必须是这个类型
aimuint16_t目标脉宽（μs）脉宽最大 2490，16 位足够；整数因为它是「用户意图」，不需要小数
timeuint16_t运动总时长（ms）上限 10000ms；记录它便于调试和后续扩展
curfloat当前脉宽（μs）必须是浮点——见下方说明，这是全工程最关键的类型选择
incfloat每 20ms 的增量必须浮点，否则小数被截断，慢速运动时会「卡住不动」
为什么 cur 必须是 float：一个能讲很久的细节

假设用 int cur。要让舵机用 5 秒从 1500 走到 1600（差 100μs），增量 = 100 / (5000/20) = 0.4。整数类型下这个值被截断成 0 → cur += 0 → 舵机永远不动。这就是「慢速小位移」在整数实现下的经典死锁。

用 float 后，每次 cur += 0.4，累计 250 次正好到 1600。代价是每次运算要几十个时钟周期（F103 没有硬件 FPU，浮点是软件模拟）。算一下负载：8 路 × 每秒 50 次 = 400 次浮点加法/秒，对 72MHz 的 M3 来说完全无压力（每次约 50 周期 → 2 万周期/秒，占 0.03%）。

结论：这个场合用浮点是正确的，因为「低频率 + 低精度要求」把浮点的成本摊平了。 如果换成 1kHz 的控制频率或者 8 路以上，就该改用「定点数」（比如把脉宽放大 16 倍存成整数），这是嵌入式里常见的优化手段。

全局数组 duoji_doing[DJ_NUM] 就是 8 份这样的状态。DJ_NUM = 8 而实际只用 6 路——多出的 2 路是占位，因为定时器中断按 8 个时隙循环，多留两个空槽可以让周期计算保持整数，不需要特判。

7.2 限位表：给每个舵机配独立的「安全活动范围」

Hardware/servo/h_servo.c · 21-46 行每路舵机独立的 PWM 上下限

为什么需要这张表？三个理由：

  1. 机械结构限制：4 号舵机（腕部角度调节）的机械行程只有 ±90°，如果给它 510~2490 的完整范围，转到 0° 或 180° 就会顶住结构、堵转烧毁。所以单独限到 833~2167。
  2. 防止自碰撞：某些姿态下大臂和小臂会撞在一起。限位是软件层面的「禁区」。
  3. 可配置性：如果换了机械臂构型，只改这个数组即可，不用动任何逻辑代码——把「常量」和「逻辑」分离，是良好设计的标志。

限位在两个地方被检查（duoji_doing_set 和 servo_inc_offset）。这不是冗余，而是防御性编程：前者防「用户给了非法目标」，后者防「浮点累计漂移导致越界」。

7.3 servo_init()：那两行「先置高再配模式」的安全措施

Hardware/servo/h_servo.c · 58-87 行初始化 6 路舵机引脚

注意顺序：GPIO_SetBits(...) 在前，GPIO_Init(...) 在后。

顺序反了会烧舵机（这不是夸张）

STM32 复位后，所有 GPIO 的 ODR 寄存器是 0。如果你先 GPIO_Init 配成推挽输出、再 GPIO_SetBits 拉高，中间会有几十到几百纳秒的窗口，引脚输出低电平。

对舵机来说，「持续低电平」= 0μs 脉宽 = 无效信号。有些舵机会忽略它；但有些舵机会把它当成「最小脉宽」，瞬间全速转向 0° 位置——6 路同时猛转，电流冲击可能拉垮电源，甚至扫齿。

先写 ODR 再配模式，引脚从「高阻输入」直接变成「输出高电平」，中间没有任何低电平窗口。这个技巧在驱动继电器、MOS 管、舵机时都适用，值得记牢。

另外注意 servo_init() 末尾的注释：「不再在这里初始化 duoji_doing[]，因为 main() 中已经提前初始化了」。这是防止「重复初始化覆盖掉从 Flash 读回的当前位置」——一旦覆盖，防猛动机制就前功尽弃。第 3 章讲过这个顺序依赖，这里是它的另一半。

7.4 duoji_doing_set()：五道关卡，逐行讲

Hardware/servo/h_servo.c · 127-169 行设置目标脉宽与运动时间，算出增量

这个 40 行的函数有 5 个分支，每一个都对应一种边界情况：

分支条件作用 / 为什么
①index >= DJ_NUM防数组越界。指令里写 #009P... 就会走到这里，直接返回而不是写坏内存
②aim == 0「0」被约定为停止：把 inc 清零、aim 设成当前值，舵机原地不动
③aim 超限裁剪到 servo_pwm_min/max[index]，保护机械结构
④diff < 1.0f 或 time < 20直接到位：差值不足 1μs（肉眼不可见）或时间不足一个更新周期时，没必要插值，直接 cur = aim; inc = 0
⑤其它正常路径：算出 inc，交给定时器中断慢慢逼近

关键是第 ⑤ 分支的那个公式：

inc = (aim − cur) / (time / 20)

物理含义：把总位移平均分配到「时间 / 20ms」个台阶上。因为定时器中断每轮会给每个舵机更新一次 cur，而一轮正好 20ms（第 8 章会证明），所以每 20ms 走一步 inc，走 time/20 步就到位。

举例：从 1500 到 2000，时间 1000ms → inc = 500 / 50 = 10，即每 20ms 走 10μs，50 步 = 1 秒到位，速度恒定 500μs/s。这就是「匀速运动」的实现方式——梯形速度曲线的最简版（没有加减速段）。

为什么 time 上限是 10000ms

time 字段是 uint16_t，最大 65535，理论上可以更大。限制到 10000 是产品层面的选择：一是超过 10 秒的运动在示教场景里没意义；二是 inc 会变得极小（比如 100μs/10s = 0.2），浮点累计误差相对变大。这是一个「用业务约束简化数值问题」的例子。

7.5 servo_inc_offset()：中断里的「一步」

Hardware/servo/h_servo.c · 179-203 行定时器中断每轮调用一次，让 cur 向 aim 逼近一步

这个函数在 TIM2 中断里被调用（每个舵机每轮一次），逻辑很简单：

  1. if (inc != 0)：只有正在运动时才做事。静止的舵机每轮只做一次判断，几乎零开销。
  2. 再裁剪一次 aim_temp：防御「运动过程中有人改了限位表」或「浮点漂移」。
  3. diff < 1.0f → cur = aim_temp; inc = 0;。这就是「到达」的判定。用 1.0 而不是 0，是因为浮点累加几乎不可能精确命中——比如每次加 0.4，加到 1599.9999 就永远不会等于 1600。设一个死区，到了就「吸附」过去，这是浮点比较的标准做法。
  4. 否则 cur += inc，前进一步。
「浮点不能用 == 比较」这条规矩，在这里体现得很具体

工程里唯一一处浮点相等比较在 app_servo_save_pos_check() 里：if (duoji_doing[i].inc != 0)。这里是可以的——因为 inc 要么被赋值为精确的 0.0（停止/到达时），要么是计算出来的非零值，不会出现「本该是 0 但算出 1e-17」的情况。能判断「这个 == 是安全的」比死记「不要用 == 」更有价值。

7.6 实际速度误差：一个你可能没注意的 4% 偏差

公式假设「每 20ms 更新一步」，但第 8 章会证明：8 路舵机一轮的真实周期是 20ms（理想）到 20.4ms（最坏）。取平均 20.2ms 算一下：

实际用时 = (time/20) × 20.2ms ≈ time × 1.01  →  比设定慢约 1%

1% 的误差在示教场景完全无感（1 秒的动作慢 10ms）。但如果哪天你要做「多臂同步」或者「配合视觉节拍」，这个误差就会累积成可见的不同步。届时正确的做法不是调公式，而是把「每轮更新」改成「按实际经过时间更新」：

/* 改成按真实时间推进，与更新周期解耦 */
float dt = (millis() - last_ms) / 1000.0f;
cur += speed * dt;              /* speed 单位 us/s，存进结构体即可 */
本章的设计思想提炼

「目标值 + 当前值 + 增量」这个三元组，是几乎所有运动控制的通用骨架：3D 打印机的步进插补、无人机的姿态环、游戏引擎的缓动动画，本质都是它。区别只在「增量怎么算」——本工程用最简单的线性插值（恒定速度）；进阶会用梯形/S 曲线（起步加速、末段减速），运动更柔和、冲击更小。

如果你要给这个项目加一个「S 曲线」升级，只需要改 duoji_doing_set 里 inc 的计算方式，加上加减速段，其它代码一行不用动——这就是良好分层带来的可改造性。

8最硬核的一章：用定时器中断手动生成 8 路 PWM

如果这份讲义只讲一章，就该讲这一章。因为「用一个定时器 + 16 次中断，生成 8 路独立可调的 50Hz PWM」是整个工程里最不像「常规写法」、也最能体现嵌入式思维的地方。

8.1 为什么不用硬件 PWM：一个被引脚绑死的现实

STM32F103 的定时器有硬件 PWM 模式：配好 ARR（周期）和 CCR（占空比），波形由硬件自动输出，CPU 一次都不用管。这显然是「正确」的做法。但本项目做不到，原因有三层：

  1. 通道数量不够：F103C8 只有 TIM1（4 通道）、TIM2/3/4（各 4 通道）。要用硬件 PWM，必须把多路舵机挂到同一个定时器的不同通道上。而 6 路舵机需要 6 个通道，至少跨两个定时器。
  2. 引脚固定死：TIM2_CH1 只能是 PA0（或重映射到 PA15），TIM3_CH1 只能是 PA6……而这块板子的舵机接在 PB3/PB8/PB9/PB6/PB7/PB4。这几个引脚里，只有 PB6/PB7 恰好是 TIM4_CH1/CH2，其余全部对不上。
  3. 改引脚 = 改 PCB：对一个已经打样、焊接、装配好的机械臂来说，这等于推翻硬件重来。
所以作者选了「软件 PWM」

思路是：让一个定时器产生高频中断，每次中断只做一件事——翻转某一根引脚，并把定时器下一次的「闹钟」设成「这根引脚还需要保持多久」。 8 路 × 高低两段 = 16 次中断构成一个完整周期。

代价是 CPU 要频繁进中断；收益是不用改硬件、引脚可以任意分配、后期想加第 7 路舵机只改一个宏。这是一个典型的「用软件复杂度换硬件自由度」的工程决策，在这种教学/小批量产品上非常合理。

8.2 TIM2_Init(2000, 72 - 1)：把定时器调成「微秒表」

Hardware/timer/h_timer.c · 79-106 行TIM2 初始化：1MHz 计数、开更新中断、最高抢占优先级

参数含义要算清楚：

计数频率 = 72MHz / (PSC + 1) = 72MHz / 72 = 1MHz → 每计一个数 = 1μs
初始周期 = (ARR + 1) / 1MHz = 2001 / 1MHz ≈ 2ms

关键洞察：计数频率被设成 1MHz，意味着「计数值 = 微秒数」。 这样一来，舵机脉宽 1500μs 就可以直接写成 ARR = 1500，不需要任何换算。这是嵌入式里常用的技巧——把单位对齐到物理量，代码里就不用换算，可读性和可调试性都大幅提升。

为什么初始 ARR 是 2000（2ms）？因为 TIM2_Init() 只是「先把定时器跑起来」，真正的周期在第一个中断进来之后就会被改写。2000 这个值没有任何特殊含义，只要「不为 0、不会立刻溢出」即可。

还有一个细节值得注意：NVIC_IRQChannelPreemptionPriority = 0（最高抢占）。为什么？

中断延迟直接等于脉宽误差

PWM 的脉宽精度，取决于「定时器溢出」到「ISR 里执行 servo_set() 翻转引脚」之间的延迟。如果这个 ISR 被别的中断抢占，延迟就会变长，脉宽就会变宽。

算一下容忍度：舵机对脉宽的敏感度大约是 1μs ≈ 0.09°（按 180° 舵机 11.11μs/°算；若按 270° 舵机则是 0.135°）。若中断延迟抖动 20μs，角度抖动 1.8°——肉眼可见的「嗡嗡」抖动。所以这个 ISR 必须是最高优先级，且体内尽量少做事。

现在回头看 TIM2_IRQHandler 里调用的 servo_inc_offset()——里面有一次浮点加法和若干比较，大约 200~400 个时钟周期（约 3~6μs）。这就是它的全部开销，可以接受。但如果有人在里面加一句 UsartPrintf()（几百微秒），舵机会立刻开始抖。

8.3 中断服务函数：一个 2 状态的「时隙状态机」

Hardware/timer/h_timer.c · 123-165 行每次中断翻转一路引脚，并设定下一次的等待时间

这几行代码需要掰开揉碎。它的核心是两个 static 变量构成的状态：

变量取值含义
flag0 / 10 = 即将进入「高电平段」，1 = 即将进入「低电平段」
duoji_index10 ~ 7当前正在处理第几路舵机

每进一次中断，做的事情是：

取当前舵机的脉宽 cur_pwm（并夹在 500~2500 之间）
├─ flag == 0（高电平段）：
│    把下一次闹钟设为 cur_pwm 微秒后 → ARR = cur_pwm
│    引脚拉高
│    更新这个舵机的 cur（向前走一步）
├─ flag == 1（低电平段）：
│    把下一次闹钟设为 (2500 - cur_pwm) 微秒后 → ARR = 2500 - cur_pwm
│    引脚拉低
│    切换到下一路舵机（index++）
└─ flag 取反

逐行解释几个容易忽略的点：

① static u8 flag / static u16 duoji_index1

必须 static。中断函数在逻辑上是「反复被调用的同一个函数」，但它不是主循环调用的，没有「调用者」帮它保存局部变量。用 static 让这两个变量常驻内存，才能在两次中断之间保持状态。

为什么不担心重入？ 因为 TIM2 中断的抢占优先级是 0（最高），没有任何中断能打断它；它自己也不会递归。所以这两个 static 变量是安全的。如果哪天你把优先级改低，并且有更高优先级的 ISR 也访问它们，就必须加临界区保护了。

② cur_pwm < 500 → 500；cur_pwm > 2500 → 2500

这是最后一道保险。为什么必须有？因为 ARR 一旦被写成 0，定时器会以最快速度反复溢出，中断频率飙升到几百 kHz，CPU 全部被中断吃掉，主循环彻底饿死——表现为「程序死机」。

cur 理论上被限位表保护着，但浮点运算、外部直接改共享变量（比如 parse_action 里的偏差校准会直接操作 cur）、或者 RAM 被踩，都可能让它变成 0 或负数。这一层夹紧是「花 4 条指令买一个不死机」，非常划算。

③ temp = 2500 - cur_pwm; if (temp < 100) temp = 100;

低电平时间也不能太短。如果 cur_pwm = 2490，temp = 10μs，那么「拉低 10μs 又拉高」——对舵机来说这几乎是连续高电平，它可能识别不出周期边界。设 100μs 下限，保证每路都有足够明显的低电平间隙。

④ 为什么 ARR 必须在中断里改，而且这样改是安全的

这是本章最精妙的一点。STM32 的 ARR 寄存器在「预装载（ARPE）关闭」时是立即生效的。如果计数器 CNT 已经跑到 1000，你突然把 ARR 改成 500（比 CNT 小），计数器会一路数到 65535 才回绕——造成 65ms 的巨大毛刺，舵机直接抖一下。

而这段代码只在更新中断里写 ARR。更新中断的含义就是「CNT 刚刚溢出归零」，此刻 CNT = 0，写任何非零的 ARR 都不会触发「ARR < CNT」的问题。「在 CNT=0 的时刻改 ARR」是软件 PWM 能够成立的前提，理解了这一点，你才真正理解这段代码。

8.4 完整时序推演：一个 20ms 周期里发生了什么

假设 8 路舵机的当前脉宽分别是 1500、2000、1200、1500、1500、900、1500、1500（后两路是空位，停在 1500）。我们把这 16 次中断完整列出来：

为什么「高 + 低 = 2500」这么重要

假设低电平时间是个固定值（比如都设 1000μs），那么总周期会变成 Σ(脉宽) + 8×1000 —— 周期会随脉宽变化：所有舵机都转到 2490 时，周期变成 8×3490 = 27.9ms，频率掉到 36Hz。舵机对周期也是敏感的（周期过长会导致内部比较器复位、力矩下降）。

而「高 + 低 = 2500 恒定」的设计，让每路占用固定的时间槽，总周期永远是 20ms，与脉宽无关。这是一个很聪明的约束选择——把「变量」限制在时隙内部，时隙本身保持恒定。

8.5 误差分析：这套方案的真实精度

ARR 装载的 +1 误差+2μs/周期周期 20.000ms → 实际 20.002ms，可忽略

8.6 CPU 占用：这笔账要算清楚

每 20ms 有 16 次中断，即 800 次/秒。每次中断的开销：

  • 硬件入栈/出栈：约 12 个周期（M3 自动压栈 8 个寄存器）
  • 取中断状态、清标志：约 10 个周期
  • 夹紧判断 + 写 ARR + 写 GPIO：约 15 个周期
  • servo_inc_offset() 里的浮点运算：约 150~300 个周期（软件浮点）

800 次/秒 × 约 300 周期 = 240 000 周期/秒 ÷ 72 000 000 = 约 0.33%

0.33% 的 CPU 占用，换来 8 路任意引脚的 PWM——这笔交易很划算。但要注意 servo_inc_offset() 是主要开销来源：如果哪天你要驱动 16 路舵机，中断次数翻倍 + 浮点运算翻倍，占用会到 1.3%，依然可接受；如果到 32 路，就该考虑把浮点换成定点，或者把「推进 cur」这件事挪到主循环里做（中断只负责翻转引脚）。

8.7 这套方案还能怎么优化

  1. 改用硬件 PWM：如果重新设计 PCB，把 6 路舵机集中到 TIM3/TIM4 的通道引脚上，就能完全释放 CPU，且精度更高（硬件比较，无中断延迟）。这是「治本」方案。
  2. 改用 DMA + 定时器：用 DMA 把「脉宽序列」搬到 GPIO 的 BSRR 寄存器，配合定时器触发，可以做到 CPU 零参与。代价是复杂度陡增，小项目不值。
  3. 把浮点推进挪出中断：中断里只读 cur，主循环里更新 cur。这样 ISR 只花几十个周期，抖动更小。但要处理好「主循环被阻塞时 cur 不更新」的一致性。
  4. 给 ARR 加预装载（ARPE）：TIM_ARRPreloadConfig(TIM2, ENABLE) 后，写 ARR 会等到下一个更新事件才生效，彻底避免「ARR < CNT」的毛刺风险。本工程靠「在 CNT=0 时写」规避了这个问题，开启 ARPE 是更稳妥的做法。
本章必须记住的三句话

① 「高 + 低 = 固定值」是软件 PWM 周期稳定的关键；
② 写 ARR 必须在 CNT = 0 的时刻（更新中断里）；
③ 中断服务函数里每多一条语句，都会变成舵机的角度误差。

9指令解析：把一串字符变成六个舵机的目标值

第 6 章解决了「怎么把字节收齐」，这一章解决「收齐的字符串怎么变成动作」。核心文件是 app_servo.c，它有 759 行，是整个工程最大的文件。

9.1 parse_action() 全貌：四个分支，一条主线

Application/app_servo/app_servo.c · 82-256 行parse_action()：整个舵机指令的解析入口

175 行看起来唬人，其实结构非常清晰：开头三个 if 是「特殊命令」，最后一大段 while 是「通用解析」。

分支触发条件处理内容
① PSCK#NNNPSCK±BBB!舵机偏差校准（存 Flash）
② PDST#NNNPDST!停止指定舵机（255 = 全部）
③ PR#NNNPR±DDDDTMMMM!相对定位（从当前位置加减）
④ 通用#NNNPppppTmmmm!绝对定位，可一条里含多组

函数第一行是 zx_uart_send_send(uart_receive_buf);——把收到的指令原样回发到两个串口。作用是让上位机确认「我收到了」，同时方便调试。这个副作用要留意：回发会占用串口发送时间，而且如果上位机也在监听，会看到自己发的数据被弹回来。

9.2 分支①：偏差校准 PSCK，一个「会改硬件行为」的命令

先解释为什么需要它。舵机是廉价机械件，同一批货的「中位脉宽」可能分别是 1490、1502、1488……如果你给所有舵机都发 1500，机械臂的初始姿态就是歪的。校准就是给每个舵机记一个补偿量，之后所有指令都自动加上它。

看代码（第 91~125 行）：

  1. uart_receive_buf[0] == '#' && [4]=='P' && [5]=='S' && [6]=='C' && [7]=='K' && [12]=='!'：这种「逐字符对齐比较」的写法，前提是指令长度固定（13 个字符）。它比 strncmp(buf+4, "PSCK", 4) 更快、更省栈，但极其脆弱——上位机多发一个空格就会失配。这是一种「用格式约束换取解析速度」的典型取舍。
  2. index = (buf[1]-'0')*100 + (buf[2]-'0')*10 + (buf[3]-'0')：把 3 个 ASCII 数字字符转成整数。这是 C 里最基本也最重要的技巧：字符 '0' 的 ASCII 是 0x30，所以 '7' - '0' = 7。整个工程里所有的「字符串转数字」都是这个模式。
  3. 核心的三行赋值（第 110~112 行）： 
    duoji_doing[index].cur = duoji_doing[index].cur
                       - eeprom_info.dj_bias_pwm[index] + bias;
eeprom_info.dj_bias_pwm[index] = bias;
    先减去旧偏差、加上新偏差，再把新偏差存起来。因为 cur 是「已经加过旧偏差的物理脉宽」，换偏差时必须先把旧的补偿撤回，否则偏差会越改越偏。这个「先还原再重算」的顺序很容易写反。
  4. aim = cur; inc = 0.001;：不改变舵机位置，但给一个极小的 inc。为什么不用 inc = 0？因为 inc = 0 表示「静止」，而 app_servo_save_pos_check() 只在「所有 inc 都为 0」时才保存位置——设成 0.001 相当于告诉系统「我还在动，先别存」，避免校准的中间状态被写进 Flash。这是个很细的心思。
  5. rewrite_eeprom()：立刻写 Flash。校准是低频操作（一次装配只做几次），所以不用考虑擦写寿命。
偏差值与脉宽的换算

偏差单位是 μs，范围 ±500。按 1μs ≈ 0.09° 换算，±500μs = ±45°。实际装配误差通常只有几度（±50μs 以内），所以 ±500 的范围很宽松——这也是为什么 other_init() 里用 500 作为「数据是否被写坏」的判据。

9.3 分支②：停止 PDST

#001PDST! 的含义是「让 1 号舵机立刻停住」。实现只有两行：inc = 0; aim = cur;——把目标设成当前值，增量清零，于是定时器里 cur += 0，舵机保持不动。

index == 255 时循环处理全部 8 路。为什么用 255 而不是 8？因为 255 是「保留地址」的惯例写法（类似广播地址），且 index 是 u16 但从 3 位十进制解析，最大 999，用 255 不会与任何真实舵机号冲突。

这个命令在 PS2 手柄里用得极多：按键按下时发「转过去」，松开时发「停住」（见 13 章的手柄命令表）。

9.4 分支③：相对定位 PR，手柄连续控制的关键

绝对定位 #004P1500T1000! 只能「转到某个固定位置」。而玩手柄时需要的是「按住就持续往一个方向走」——这就需要相对定位：#004PR+0500T1000! 表示「从当前位置再加 500μs」。

解析这一段（第 168~214 行）用了和分支①②不同的手法——用 while 循环逐字符累加，而不是固定下标。原因很简单：+0500 的位数可能变化（+50、+5000），不能写死下标。

  1. j = 6; if (buf[j] == '-') { sign = -1; j++; }：先看符号位。注意它只处理「第 6 位是 + 或 -」的情况，若既不是 + 也不是 -，j 保持 6，循环会把第一个字符当数字解析——如果那是字母，'A' - '0' = 17，会产生垃圾值。这是缺少格式校验的地方。
  2. while (buf[j] && buf[j] != 'T')：以 T 为界，把中间的字符累加成增量。delta = delta*10 + (c - '0') 就是「每读一位，把已有值乘 10 再加新位」——这就是手写的 atoi。
  3. int new_aim = (int)duoji_doing[index].cur + delta;：关键点——基准是 cur（当前实时位置），不是 aim。如果连续两次 PR 命令在不同时刻到达，用 cur 才能保证「每次都从真实位置起步」。
连续 PR 会导致「速度叠加失真」

手柄每 50ms 检测一次按键，如果一直按着，会连续发 PR 命令。此时 duoji_doing_set 每次都会重算 inc：inc = (cur + delta - cur)/(time/20) = delta/(time/20)。所以速度其实由 delta/time 决定，而不是由「按了多久」决定。

实际效果：按住 = 以固定速度前进；松开 = 立刻停。这正好是想要的。但如果按键抖动导致 50ms 内按下又松开，会先发一个大 delta 的 PR 再发 PDST，表现为「顿一下」。修法是在 duoji_doing_set 里对「同方向小步长」做合并。

9.5 分支④：通用状态机，一段值得反复读的循环

这是整个工程里复用率最高的代码——模式 2（单舵机）和模式 3（多舵机）都走这一条路径，因为它是「遇 # 就开一组」的循环。

核心循环（第 216~255 行）：

  1. len = strlen(...); while (buf[i] && (i <= len))：注意条件写了 i <= len 而非 i < len。这是为了让循环多走一步，处理字符串末尾的情况（因为缓冲区里 '\0' 之后可能还有残留数据）。这种写法略危险——一旦 '\0' 被跳过，就会继续读后面的垃圾字节，直到 i > len 才停。
  2. 四个 if/else if 分支分别处理 #、P、T 和其它字符。状态隐含在「上一次遇到的是哪个字母」里，不需要显式状态变量——因为 P 后面的数字一定是脉宽，T 后面的数字一定是时间。
  3. 三个 while 内循环负责把数字读完，index / pwm / time 被逐个填上。
  4. 最关键的是 T 分支的结尾（第 248~249 行）： 
    pwm += eeprom_info.dj_bias_pwm[index];
duoji_doing_set(index, pwm, time);
    在校准偏差被加上的这一刻，动作才真正生效——这就是「遇到 T 才算一组完整指令」的设计。所以 #001P1500T1000!#002P2000T1000! 会被拆成两组依次执行，而不是先解析完再一起执行。这意味着第一组已经在动了，第二组还在解析——对多舵机「同时起步」有细微影响（相差几微秒，可忽略）。
这段代码的可改进之处（也是极好的练习）

① 没有边界检查：index 直接来自输入，若上位机发 #999P1500T1000!，index = 999，之后 duoji_doing_set(999, ...) 会被函数开头的 if (index >= DJ_NUM) return; 拦住——但第 248 行的 eeprom_info.dj_bias_pwm[999] 没有被拦，直接越界读！ 这是一个真实存在的越界漏洞。

② 没有校验尾字符：if (buf[i] == '!') 没有出现在通用分支里，所以即使串口传来一条没有 ! 的残缺指令（比如因为丢包），也会照常执行。

练习建议：给这个循环加上 if (index >= DJ_NUM) break; 和「必须以 ! 结尾」的校验，就能修掉上面两个问题（见第 16 章练习 3）。

9.7 str_contain_str()：手写的「子串查找」

Application/app_servo/app_servo.c · 615-644 行不用 string.h 的子串查找，返回 1 起始的位置

功能等价于 strstr()，但返回的是位置（从 1 开始）而不是指针，未找到返回 0。为什么要自己写？可能的原因：早期用的是没有 string.h 的编译环境，或者想省掉 strstr 的代码体积。

算法是「朴素匹配（Naive）」，核心在失败回退那一行：

str_temp1 = str_temp1 - (str_temp2 - str2) + 1;
str_temp2 = str2;

含义：内层循环已经让 str_temp1 往前走了 k = (str_temp2 - str2) 个字符，现在要退回「起始位置 + 1」，也就是从下一个字符重新开始尝试。这是手写字符串匹配的经典写法，时间复杂度 O(n×m)，最坏情况（如 aaaaab 里找 aaab）会退化。

这段代码有一个真实缺陷

内层 while (*str_temp2) 循环中，如果 str_temp1 先遇到了 '\0'（主语串提前结束），*str_temp1++ 会一直读越界，直到碰巧和 *str_temp2 不等才退出。虽然多半不会崩，但属于「未定义行为」。

正确写法是先判断 *str_temp1 是否为空。这也是第 16 章建议你修的一个点。

本章小结

解析层的设计哲学是：用「固定格式 + 逐字符扫描」换取「零内存分配、零依赖」。它没有 sscanf（虽然 parse_cmd 里用了一点）、没有动态内存、没有正则，全部是指针和 while。好处是确定性极强（不会有 malloc 失败），坏处是脆弱（格式一变就崩）。

你未来写嵌入式协议解析时，可以采用「状态机 + 显式边界检查」：把「找帧头 → 收载荷 → 校验 → 分发」分成四个明确状态，每个状态都做边界检查。代码会长一点，但不会因为上位机多发一个空格就行为诡异。

10.1 存储布局：地址是怎么算出来的

为什么把配置块放在「最后一个扇区」

三个原因：① 动作组从地址 0 往上长，配置块从顶部往下，两边不会打架；② 配置块固定占一个扇区，擦除时不会误伤动作组；③ 如果哪天动作组数量暴增，只要不越过 8MB - 4KB 就绝对安全。

注意 ((8<<10)-4)<<10 这个写法：8<<10 = 8192（KB），减 4 变成 8188，再 <<10 乘 1024 得字节地址。用「移位」表达 KB/MB 换算在嵌入式里很常见，但可读性差——如果写成 8*1024*1024 - 4096 或 (8*1024-4)*1024，任何人一眼就懂。这是一个「为了显得高效而牺牲可读性」的反面例子（现代编译器会把两种写法编译成完全相同的代码）。

动作组在 Flash 里的内容就是一个 ASCII 字符串，不是二进制结构体：

地址 = n × 256 处存放：
[G0005#000P1500T1000!#001P2000T1000!#005P0600T1000!]\0 ......（剩余补 0 或 0xFF）

用字符串而不是二进制，好处是调试极其方便——用 $PTG:5-5! 把原始内容打出来，人眼就能读懂。代价是占空间（一个动作组通常 80~200 字节，接近 256 上限）。这个取舍很符合「教学项目」的定位。

10.2 save_action()：写入一组动作

Application/app_servo/app_servo.c · 267-317 行保存动作组 / 设置预命令到 Flash

这个函数有三个入口，先看主路径（<Gxxxx...>）：

  1. action_index = (str[2]-'0')*1000 + ... + (str[5]-'0')：从 <G0005#... 里取出 4 位编号。所以格式必须严格是 <G + 4 位数字 + #。
  2. if (action_index == -1 || str[6] != '#')：action_index 是 s32，从 4 位数字算出不可能为 −1——这行判断永远不成立，是历史遗留的死代码。真正起作用的只有 str[6] != '#'。
  3. if ((action_index * ACTION_SIZE % 4096) == 0) w25x_eraseSector(...)：只有当写入地址正好落在扇区边界时才擦除。因为 256 × 16 = 4096，所以编号是 16 的倍数（0、16、32…）时擦一次扇区，之后连续 16 组共用这个已擦除的扇区。
  4. str_replace(str, '<', '['); str_replace(str, ']', '>');：把首字符 < 换成 [，把尾字符 > 换成 ]（注意第二个参数写的是 ']'，先找 ] 再换成 >）。目的是避免存储的字符串里再出现 </>，否则下次经串口读出来再发回去时，会被误认为是新的存储指令。
  5. w25x_write(str, ...)：注意这个宏展开是 spi_flash_write_no_check()——不做擦除检查，直接写。
这里有一个真实的数据丢失 Bug（很值得研究）

因为写入用的是 write_no_check（不检查、不擦除），而擦除只在「编号是 16 的倍数」时发生——如果你把同一个动作组（比如第 5 组）保存两次，第二次会写失败。

原理：Flash 只能把 bit 从 1 写成 0。第一次写入后，某些 bit 已经是 0；第二次写入需要把这些 bit 变成 1（因为新内容不同），而 Flash 做不到——结果就是新旧内容「按位与」在一起，字符串变成乱码或提前遇到 '\0' 而截断。

表现：用户「改了第 5 组动作，重放却发现还是旧动作，或者干脆不动作」。这种 bug 极难排查，因为没有任何报错。

修法三种：① 保存前强制擦除所在扇区（会牺牲同扇区其它 15 组的数据，需要先读出来合并）；② 每次保存前把整个扇区读到 RAM，改完再整扇区写回（就是 w25x_writeS = SpiFlsahWriteS 干的事）；③ 给每个动作组加「版本号/序号」，写入时追加而不是覆盖。

注意配置块用的是 w25x_writeS（带擦除检查），所以 rewrite_eeprom() 没有这个问题——同一个工程里两种写入方式并存，恰恰说明作者踩过坑后只修了一处。

另外两个入口：

  • if (str[1] == '$' && str[2] == '!') → 清空预命令（<$!>）。把校验位置 0，下次上电就不会执行预命令。
  • else if (str[1] == '$') → 设置预命令（<$DGT:1-5,3!>）。含义是「每次上电自动执行这串命令」。str[strlen-2] = '\0' 是为了去掉结尾的 >。

三件事：切 SPI 模式 → 读 256 字节 → getMaxTime() 算时长 → parse_action() 执行。

getMaxTime() 的作用是算出这一组动作里最长的运动时间：

Application/app_servo/app_servo.c · 677-695 行找出一组动作里最大的 T 值

为什么要取最大值？因为一组动作里的 6 路舵机是同时启动的，各自用不同的时间走到目标。整组动作「完成」的时刻，是最慢那一路到位的时刻。所以 action_time 必须取 max——如果取平均，下一组动作会在慢的那路还没到位时就启动，造成「动作被截断、轨迹变形」。

10.5 配置块的写入与「自动保存位置」

每次调用都是「擦一整个扇区 + 写回结构体」。w25x_writeS（= SpiFlsahWriteS）内部会先读整扇区、擦除、合并、再写回——所以它既慢（约 100ms）又消耗擦写寿命。

正因为这样，作者给「自动保存位置」加了三重节流：

Application/app_servo/app_servo.c · 507-549 行每 30 秒检查一次，仅在"全部静止且位置变化"时保存
  1. if (millis() - last_save_time < 30000) return;：时间节流——30 秒内最多检查一次。
  2. if (duoji_doing[i].inc != 0) { all_idle = 0; break; }：状态节流——有任何一路在动就不存，避免存到「运动中间态」。
  3. if (cur_pos != eeprom_info.last_pos[i]) pos_changed = 1;：变化节流——位置没变就不写，避免无谓擦写。

三个条件同时满足才写 Flash。算一下寿命：假设用户每 30 秒动一次机械臂，一天 8 小时工作 → 约 960 次/天。W25Q64 的扇区擦写寿命典型值 10 万次 → 约 104 天就该坏了。

这是一个真实的寿命隐患

30 秒一次的「无条件可写」对 Flash 来说太频繁了。更好的策略：

① 只在「关机前」保存（检测电源电压下降，或用按键主动保存）；
② 加长节流到 5~10 分钟；
③ 轮换写入（用 4 个扇区轮流写，寿命 ×4）；
④ 更根本的：位置本来就不该频繁保存——机械臂每次上电都会归位，保存「上次位置」的意义主要是防猛动，只需要在「手动摆完姿态后」保存一次即可。

这个例子很好地说明了「功能正确 ≠ 工程设计正确」。写代码时多想一步「这个操作会重复多少次、硬件能承受多少次」，是从「能跑」到「可靠」的分水岭。

还有一个小细节：它复用了 uart_receive_buf 作为读缓冲。如果此时正好有串口数据在接收，就会冲突——不过因为它在主循环里执行，且 uart1_get_ok 为 0 时才可能被调用（实际上并没有检查），属于「靠时序侥幸」。正确做法是用一个独立的局部缓冲区（256 字节，RAM 够）。

本章要点

① 地址 = 组号 × 256，因为 256 正好等于 Flash 的一页；
② 动作组存成 ASCII 字符串，牺牲空间换可调试性；
③ 擦除只在扇区边界发生 → 重复保存同一组会失败（真 Bug）；
④ action_time 必须取组内最大时间，否则动作被截断；
⑤ 「每 30 秒自动存位置」对 Flash 寿命不友好，是典型的「功能对但工程不对」。

11逆运动学：从「我想让爪子到那个点」到「六个舵机各转多少度」

这是全工程唯一的「数学章节」，也是最能体现「会写代码」和「会做机器人」差别的地方。正运动学是「已知关节角度，算末端位置」（简单，三角函数一路乘下去）；逆运动学是反过来的，且往往有多解或无解。

11.1 坐标系与自由度

四个关节里，只有 θ6 是「转出平面」的，其余三个都在同一个垂直平面内。这个结构带来了一个极其重要的简化：

降维：3D 问题被拆成「1 个旋转 + 1 个平面三角形」

因为 θ5/θ4/θ3 都只能在垂直平面里动，所以舵机 1/2/3 的求解只跟「目标点离底座的水平和垂直距离」有关，与目标在哪个方位无关。于是：

① 先用 θ6 把「目标方位」对齐 → 一个 atan2 解决；
② 再用 (y', z') 两个量解平面内的三连杆 → 余弦定理解决。

这就是为什么这个逆运动学只有 168 行——结构简单是算法简单的前提。如果加一个「手腕俯仰 + 手腕翻转」（6 自由度），就必须上矩阵和 D-H 参数了。

if (x == 0) theta6 = 0.0f;
else        theta6 = atan2(y, x) * 270.0f / PI;

为什么用 atan2(y, x) 而不是 atan(y/x)？因为 atan 只能返回 −90°~+90°，无法区分「第一象限」和「第三象限」——目标在 (−100, −100) 和 (100, 100) 时 y/x 都是 1，atan 给出同一个角，机械臂会转到完全相反的方向。atan2 通过两个参数的符号能区分四个象限，返回 −180°~+180°。

这也是为什么代码要先判 x == 0：atan2(y, 0) 在数学上是合法的（返回 ±90°），但作者选择了「x 为 0 就当 0°」——这是一个业务决定（正前方为基准），不是数学必需。

11.3 第二步：投影 + 减掉爪子（最容易算错的一步）

y = sqrt(x*x + y*y);                              /* ① 水平距离 r */
y = y - l3 * cos(Alpha * PI / 180.0f);            /* ② 退掉爪子长度 */
z = z - l0 - l3 * sin(Alpha * PI / 180.0f);       /* ③ 减底座高 + 退爪子 */

这三行的核心思想是：把「爪子尖的目标位置」换算成「腕关节的位置」。因为后面的三连杆计算是以腕关节为末端的，而用户给的是爪子尖。

两个必须注意的符号：

  • z = z - l0 - ...：因为用户给的 z 是「离地面的高度」，而连杆计算的原点在肩关节（离地 l0）。所以先减掉底座高度，把原点搬到肩上。这是坐标系平移，漏了它整个解都是错的。
  • Alpha 为负值（爪子朝下，代码推荐 −25°~−65°）：此时 sin(Alpha) 为负，z 减去一个负数 = z 变大，符合直觉——爪子朝下时，腕关节比爪子尖更高。

11.4 第三步：余弦定理求肩角 θ5 与肘角 θ4

现在问题变成纯二维：已知肩关节到腕关节的距离 Dist，以及两段臂长 l1、l2，求三角形内角。这就是初中的余弦定理：

Dist² = l1² + l2² − 2·l1·l2·cos(肘内角)
→ cos(肘内角) = (Dist² − l1² − l2²) / (2·l1·l2)

代码里把它写成了两个量：

dist_yz = sqrt(z*z + y*y);                       /* 肩到腕的距离 */
ccc = acos(y / dist_yz);                         /* 目标方向与水平轴的夹角 */
bbb = (y*y + z*z - l1*l1 - l2*l2) / (2*l1*dist_yz);  /* 大臂与目标方向的夹角余弦 */
theta5 = ccc * zf_flag + acos(bbb);              /* 肩角 = 两者之和 */
aaa = -(y*y + z*z - l1*l1 - l2*l2) / (2*l1*l2);  /* 肘内角余弦 */
theta4 = 180 - acos(aaa) * 180/PI;               /* 肘角 = 180° - 内角 */

为什么 theta5 是「两个角相加」，而不是直接一个 atan2？看下图：

zf_flag 是什么

zf_flag = (z < 0) ? -1 : +1。当腕关节低于肩关节（z < 0）时，ccc 被取负，把「向上量」改成「向下量」。这处理了「目标在肩部以下」的姿态——如果不做这个翻转，theta5 会算出 180°−xxx 的错误值。

这是一个「用条件分支代替象限判断」的土办法。更严谨的做法是用 atan2(z, y) 直接得到带符号的角度，无需 flag。代码之所以这么写，可能是因为作者是从「几何作图」而不是「解析几何」的思路推导的——这在工程代码里很常见，能跑就行，但可读性和鲁棒性会差一些。

再看 theta4 = 180 − acos(aaa)。为什么是 180 减？因为 acos(aaa) 给的是三角形内角（0°~180°，伸直时为 180°），而舵机的「肘关节角」定义是相对伸直状态的弯曲量：伸直 = 0°，完全折叠 = 180°。所以两者互补。

11.5 第四步：腕角 θ3

theta3 = Alpha + theta4 - theta5;

推导：设小臂与水平轴的夹角为 φ = theta5 − theta4（肩角减去肘部弯曲量）。而爪子要指向 Alpha，所以腕关节需要相对小臂转过的角度是：

theta3 = Alpha − φ = Alpha − (theta5 − theta4) = Alpha + theta4 − theta5

这就解释了为什么 Alpha 是「输入参数」而不是「算出来的」——爪子的姿态由用户指定（比如「保持水平」就是 Alpha=0），腕角被动跟随。这是 4 自由度机械臂的固有特性：你能控制「爪子在哪」和「爪子朝哪」，但不能既控制位置又控制全部姿态。

11.6 角度 → PWM：那个神秘的 270

kinematics->servo_pwm[i] = (int)(1500 - 2000.0f * kinematics->servo_angle[i] / 270.0f);

这个公式包含三个信息：

元素含义
1500中位脉宽。角度为 0 时输出 1500μs
2000/270 ≈ 7.4每个「角度单位」对应的微秒数
负号 1500 −角度增大时脉宽减小——因为舵机安装方向与数学坐标系相反
这里有一个「单位不统一」的隐患，值得单独说清楚

工程里存在两套角度观念：

① h_servo.h 的注释说「0.5ms→0°，2.5ms→180°」，即 11.11μs/°（180° 舵机）；
② h_kinematics.c 用 2000/270 = 7.4μs/° 的系数（270° 舵机）。

两者差 1.5 倍。而代码内部的 theta6 又是用 atan2 × 270/π 算的（也是 1.5 倍于真实角度）。这两个 1.5 倍正好互相抵消，所以最终 PWM 输出是对的——但这是一种「两个错误互相抵消」的正确，非常脆弱。

验证一下：目标 (150, 120) → 真实方位角 atan2(120,150) = 38.7°。代码算出 theta6 = 58.0（=38.7×1.5），PWM = 1500 − 2000×58/270 = 1070。若舵机是 180° 型，1070μs 对应 (1500−1070)/11.11 = 38.7°——完全正确。

教学意义：接手别人的机器人代码时，第一件事是实测标定——发 1500 看爪子指哪、发 1000 看转了多少度，用两个点反推「μs/°」。别信注释，注释经常是抄的或者过时的。

另外 kinematics_move() 里还有一行：

kinematics.servo_pwm[3] = 3000 - kinematics.servo_pwm[3];

因为腕舵机的安装方向与其它三个相反（一个正装、一个反装），所以要把脉宽绕 1500 镜像：3000 − 1500 = 1500（中位不变），3000 − 1000 = 2000（反向）。这是「用一行减法解决机械反装」的典型手法。

11.8 kinematics_move()：为什么它要「扫」一遍 Alpha

Application/app_servo/app_servo.c · 727-759 行遍历爪子角，挑一个"最舒展"的解

这段代码解决了一个逆运动学的经典问题：同一个位置有多组解。比如目标在正前方，机械臂可以「肘朝上」也可以是「肘朝下」，两者都能到，但姿态完全不同。

代码的做法是：让 Alpha（爪子角）从 0° 一路试到 −134°，记下所有能解出来的组合，取其中 i 最小（最负）的那个。

  1. if (y < 0) return 0;：只允许 y ≥ 0（前半平面）。因为底座舵机的行程是 ±90°，后半平面的目标无法到达——提前返回，省掉 135 次无效计算。
  2. for (i = 0; i > -135; i--)：以 1° 为步长穷举。注意是递减（0, −1, −2 …），所以 if (i < min) 每次都会更新 min，最终 min 是「最负的可行 Alpha」。
  3. if (i < min) { min = i; flag = 1; }：选「爪子最朝下」的解。为什么这是「最优」？因为在抓取桌面上的物体时，爪子朝下（Alpha ≈ −90°）最自然、最不容易和物体/桌面碰撞；同时「爪子越朝下」通常意味着机械臂越舒展、肘部越向外，不容易自碰撞。
  4. if (flag)：只有至少找到一个解才执行。找不到就返回 0，上位机会收到 Can't find best pos!。
  5. 用选中的 min 重新算一次（因为循环结束时 kinematics 里存的是最后一次尝试的值），然后镜像 3 号舵机、拼字符串、调 parse_action 执行。
这个「最优解」策略的三个问题

① 计算量：最坏 135 次 kinematics_analysis，每次含 4 个 acos/atan2（软件浮点，每次约 1000 周期）→ 最坏 135 × 4000 = 54 万周期 ≈ 7.5ms。对「按坐标移动」这种低频操作可以接受，但绝不能放在定时器中断里。

② 不是真正的最优：「爪子最朝下」不等于「路径最短」或「力矩最小」。真正的工业实现会用「加权代价函数」（关节行程余量 + 力矩 + 碰撞距离）来选解。

③ 步长 1° 导致抖动：如果目标只移动 1mm，扫出来的 min 可能从 −52 跳到 −53，爪子姿态突然变 1°，看起来会「抖一下」。改进方向是「记住上次的解，优先选邻近的」（这叫解的连续性 / 逆解跟踪）。

12.2 spi_write_read()：SPI 的本质是「交换」

Hardware/flash/h_flash.c · 134-152 行发一个字节，同时收一个字节

SPI 是全双工的：你每发 1 个 bit，就会同时收到 1 个 bit。所以「读」和「写」在物理上是同一个动作，区别只在「你发的东西有没有意义」。

  • 想读：发 0xFF（哑字节），收到的才是从设备的真实数据；
  • 想写：发真实数据，收到的字节丢弃。

代码里加了 retry 计数（200 次后返回 0），这是一个「防止 SPI 外设异常导致死循环」的保险。不过它有两个小问题：① 返回 0 会让调用者误以为「读到了 0」，无法区分「失败」和「读到 0」；② 200 次循环在 72MHz 下不到 3μs，如果是从设备还没准备好，可能误判失败。更稳妥的做法是「超时后置错误标志」而不是返回假数据。

12.4 写入的完整仪式：写使能 + 等忙 + 页边界

Hardware/flash/h_flash.c · 376-399 行跨页拆分的不检查写入

写操作比读复杂得多，因为有三条硬约束：

  1. 每次写之前必须发「写使能」（0x06）。这个「使能」是一次性的：执行完一条写入指令后自动失效，下次写要重新发。漏了它，写入指令会被 Flash 直接忽略（而且不报错）。
  2. 一次页编程最多 256 字节，且不能跨页回卷。如果从地址 0xF0 开始写 32 字节，会写到 0x110 —— 但 Flash 内部是「页内回卷」的，实际会绕回 0x100 覆盖开头。所以必须按页拆分成多次写入，这就是 pageremain = 256 - WriteAddr % 256 的作用。
  3. 写/擦除后必须等「忙」标志清零（spi_flash_wait_busy）。页编程约 0.7ms，扇区擦除约 45ms。如果不等待就发下一条指令，会被忽略。
为什么这里用 no_check 版本，而配置块用「带擦除」版本

spi_flash_write_no_check() 假设「目标区域已经是 0xFF」——直接写，不做擦除检查。这是调用者的责任。

动作组的场景下，调用者（save_action）确实在扇区边界做了擦除，所以「大部分情况下」这个假设成立。但如 10.2 所述，重复保存同一组时假设就破了。

而配置块用 w25x_writeS（= SpiFlsahWriteS），它内部会「读整扇区 → 擦除 → 合并 → 写回」，所以永远不会出错，代价是慢（每次约 100ms）。

这是一个绝佳的教学对照：同一个工程里的两处写入，一处图快（有隐患），一处图稳（有代价）。你在做设计决策时，要能明确说出「我在拿什么换什么」。

12.5 扇区擦除：为什么参数是「扇区号」而不是「字节地址」

Hardware/flash/h_flash.c · 406-418 行擦除一个 4KB 扇区

注意函数第一行 Dst_Addr <<= 12;：把「扇区号」乘以 4096 变成「字节地址」。所以调用时要传扇区号（0~2047），不是字节地址。

这个「参数含义与函数名不符」的设计非常容易用错。工程里的调用方式都很小心：

w25x_eraseSector(action_index * ACTION_SIZE / 4096);       /* 传扇区号 ✓ */
w25x_eraseSector(W25Q64_INFO_ADDR_SAVE_STR / 4096);        /* 传扇区号 ✓ */
spi_flash_erase_sector(0);                                  /* 扇区 0 ✓ */

如果误传字节地址（比如 4096），它会被当成「扇区 4096」→ 实际擦除地址 4096×4096 = 16MB，超出芯片容量，W25Q64 会直接忽略这条指令（不报错）。于是你看到的现象是「擦除没生效，写完还是旧数据」。

命名建议

如果这个函数叫 spi_flash_erase_sector_by_index(u32 sector_index)，并加一句注释「参数是扇区序号，不是字节地址」，就能避免 90% 的误用。这是「命名即文档」的典型案例。

13PS2 手柄：不按协议走的「协议」

PS2 手柄用的是「类 SPI」协议——有时间线、有片选、有双向数据，但不是标准 SPI：它多了一个 ACK 位，时序也有特殊要求。所以驱动只能「手动打时序」（bit-banging），不能用 STM32 的 SPI 外设。

13.1 手动打时序：ps2_transfer()

Hardware/ps2/h_ps2.c · 85-107 行手动翻转 CLK，逐位收发

这段代码是「用软件模拟硬件协议」的典型样本，逐行看：

  1. PS2_CMD((wt_data & (0x01 << i)))：把第 i 位放到 CMD 线上。0x01<<i 是「取第 i 位」的掩码，注意是从 bit0 开始，即低位先发（LSB First）。
  2. PS2_CLK(1); Delay_us(6); PS2_CLK(0); Delay_us(6); PS2_CLK(1);：产生一个「高→低→高」的时钟脉冲。PS2 协议规定：下降沿时手柄读 CMD，上升沿时手柄输出 DAT。所以先拉低再拉高，正好覆盖「发 + 收」两个动作。
  3. Delay_us(6)：PS2 手柄的时钟频率上限约 250kHz（周期 4μs），6μs 半周期 = 约 83kHz，留了充足余量。这种「宁慢勿快」的时序设计，是为了兼容劣质兼容手柄。
  4. if (PS2_DAT()) rd_data |= (0x01 << i);：读 DAT 线，同样按低位先发拼装。
标准 PS2 协议还有第 9 位（ACK）

真实 PS2 帧是 9 位：8 位数据 + 1 位 ACK（手柄拉低表示收到）。本实现跳过了 ACK 位——这在多数兼容手柄上能工作（它们不强制要求主机读 ACK），但如果用原装索尼手柄，可能会因为时序不完整而通信失败。

这也是一个「够用就好」的取舍：跳过一个 bit 换来代码简化，代价是兼容性下降。

13.2 数据帧结构：9 个字节

Hardware/ps2/h_ps2.c · 119-135 行一次完整读帧：发 2 个指令，收 9 个字节
字节内容说明
00xFF（手柄回复）—
1模式：0x41（绿灯）/ 0x73（红灯）用来判断「手柄是否连接」+「处于哪个模式」
20x5A数据开始标志（固定值）
3~4按键状态（16 位）bit = 0 表示按下，bit = 1 表示未按下（反逻辑！）
5~8摇杆模拟量本项目未使用（只用了按键）

ps2_isConnected 的判断很实用：只有模式字节是 0x41 或 0x73 才算连上。掉线时这个值会是 0x00 或 0xFF，于是 app_ps2_run 直接 return，不会拿垃圾数据去驱动舵机。

13.3 app_ps2_run()：50ms 轮询 + 变化检测

Application/app_ps2/app_ps2.c · 120-144 行每 50ms 读一次手柄，只在按键变化时处理

两个设计点：

  • 50ms 轮询：手柄的按键响应速度对人来说 20Hz 足够，50ms 也顺便限制了「按住不放时发送 PR 命令的频率」（每 50ms 一次 PR，速度稳定）。如果改成 10ms，PR 命令会发得太密，反而让 inc 被频繁重算。
  • 变化检测 if (psx_button_bak[0] != psx_buf[3] || ...)：只有按键状态变了才处理。这是「边沿触发」而不是「电平触发」——按住不放只会触发一次「按下」，不会连续触发。

13.4 app_ps2_buf()：用 XOR 找出「哪些位变了」

Application/app_ps2/app_ps2.c · 245-291 行解析 16 位按键，按「按下/松开」分别执行命令

核心技巧：

current = buf[0] << 8 | buf[1];      /* 拼成 16 位 */
changed = bak ^ current;             /* 异或：哪些位变了 */
for (i = 0; i < 16; i++)
    if (changed & (1 << i)) {       /* 只处理变化的位 */
        if (!(current & (1 << i)))  /* 当前为 0 → 按下 */
            ...按下命令...
        else                         /* 当前为 1 → 松开 */
            ...松开命令...
    }

XOR 找变化位是处理位图状态的标准手法，值得记住。判断「按下/松开」时要注意反逻辑：current 的该位为 0 才是按下。

末尾还有三行：beep_on(); Delay_ms(10); beep_off();——每次按键变化响一声。这 10ms 阻塞在主循环里，虽然短，但在「连续快速按键」时会造成轻微卡顿。更好的做法是「置一个标志，由非阻塞的蜂鸣器状态机去响」。

13.5 命令表：用「字符串 + 分隔符」做按键映射

Application/app_ps2/app_ps2.c · 54-71 行红灯模式的按键命令映射表

这个设计的巧妙之处在于：按键映射不是硬编码在 C 代码里的 if-else，而是一张「字符串表」。

格式：<PS2_RED01:按下命令^松开命令>

  • ^ 前面是「按下时执行」的命令，后面是「松开时执行」的命令；
  • 命令本身是串口指令（#005P0600T2000! 或 $DJR!），可以直接喂给 parse_action / parse_cmd。

带来的好处：改按键功能不用动逻辑代码，只改这张表就行；甚至可以通过串口现场改写（虽然本工程没做这个功能）。

绿灯模式和红灯模式的区别

红灯模式（0x73）：按键直接控制 6 个舵机（适合机械臂）。
绿灯模式（0x41）：按键发送 $DCR:... 命令（控制轮式底盘的四轮速度，适合「机械臂 + 小车」组合平台）。
本工程只实现了机械臂部分，所以绿灯模式下发的 $DCR 命令在 parse_cmd 里没有对应分支，会被忽略。这说明这份代码是从一个「机械臂 + 移动底盘」的完整平台里裁剪出来的。

13.6 extract_ps2_cmd()：从字符串里「挖」出命令

Application/app_ps2/app_ps2.c · 161-201 行按 ^ 分隔符提取「按下」或「松开」那一半

逻辑是纯字符串查找：找到 : 作为起点，找到 ^ 或 > 作为终点。

  • 按下（is_release = 0）：起点 = : 后，终点 = ^（若有）否则 >。
  • 松开（is_release = 1）：起点 = ^ 后，终点 = >。

注意它用 memcpy(dest, start, len) 而不是 strncpy，并手动补 '\0'。这是正确的做法——strncpy 在源串比 n 短时会用 0 填满剩余空间，反而浪费。

13.7 execute_ps2_cmd()：为什么要关中断

Application/app_ps2/app_ps2.c · 210-231 行把提取出的命令送进解析器，期间关闭 USART1 接收中断

这三行 usart1_close(); ... usart1_open(); 构成了一个临界区，保护的是 uart_receive_buf 和 cmd_return 这两个全局缓冲区不被串口中断改写。

为什么要保护？因为 parse_action() 内部会往 cmd_return 里 sprintf（比如 kinematics_move 生成多舵机指令），如果此时串口中断正在往 uart_receive_buf 写数据，两个缓冲区就可能互相踩。

这个保护并不完整

① 只关了 USART1，没关 USART3——如果总线口正好在收数据，照样会写 uart_receive_buf；
② 关闭中断期间如果来了数据，会丢掉（因为 RXNE 中断被禁，硬件只能缓存 1 个字节，之后溢出）；
③ 更彻底的做法是「给 cmd_return 用独立缓冲区」或「用互斥标志」。

但方向是对的：「共享缓冲区 + 中断」必须有某种保护机制。这个工程用「关中断」这种最原始的方式，虽然不完美，但比什么都不做强得多。

本章要点

① SPI 的本质是「交换」，读要发哑字节；
② Flash 写入必须「写使能 + 等忙 + 不跨页」，漏一步不报错；
③ erase_sector 的参数是扇区号不是地址；
④ PS2 是「类 SPI」，要手动打时序，bit=0 才是按下；
⑤ 按键映射用字符串表而不是 if-else，改功能不用改逻辑。

14上位机与联调：让代码和软件「对上话」

工程里的 上位机/ 目录有三个文件：Yeahbot V1.13.exe（PC 软件）、config.ini（软件配置）、Am1视觉机械臂动作组.ini（动作组数据）。搞清它们的关系，你才能自己写一个上位机。

14.1 串口参数：不匹配就全是乱码

参数本项目值说明
波特率115200两路串口都是（Usart1_init(115200) / Usart3_init(115200)）
数据位 / 停止位 / 校验8 / 1 / 无即 8-N-1

新手最常踩的三个坑

① 串口助手勾了「发送新行」→ 指令变成 #001P1500T1000!\r\n，虽然解析器遇到 ! 就结束了（多余字符不影响），但存储指令 <...> 后面多出的 \r\n 会被写进 Flash，下次读出来就多了垃圾；
② 用了 USB 转串口模块但没接地线（只接了 TX/RX）→ 通信时好时坏；
③ 接的是 USART3（PB10/PB11）却在软件里选了 USART1 那个 COM 口。

14.2 config.ini：上位机把「按键映射」也存成配置文件

看这个文件的结构（节选自工程）：

[PS2]
cmd=<PS2R_L20^R_L21^...>      ← 每个按键的"名称"
fun=<><><>...                  ← 每个按键绑定的"功能"（空=未绑定）

[servo]
group={G0000#000P1500T1500!...}{G0001...}   ← 所有动作组，大括号分组

这个设计说明：上位机把「动作组数据」存在本地 ini 里，需要时才通过串口下发到单片机。所以有两份数据：

  • PC 端 ini：完整备份，可以编辑、导出、分享；
  • 单片机 Flash：当前生效的副本。

两边可能不一致——比如你从没下发过，那 Flash 里是空的。联调时如果「软件里能看到动作，但机械臂不动」，第一件事是确认数据是否已经下载到 Flash（可以发 $PTG:0-0! 回读验证）。

14.3 自己写一个上位机（最小可用版）

你完全可以用 Python 写一个 40 行的上位机，比啃别人的 exe 更有价值：

import serial, time

ser = serial.Serial('COM3', 115200, timeout=0.2)

def send(cmd):
    """发送一条指令，等待回显"""
    ser.write((cmd + '!').encode())
    time.sleep(0.05)
    print(ser.read(ser.in_waiting or 1))

# 单舵机：0 号转到 1500us，用时 1s
send('#000P1500T1000')

# 多舵机同时动作（用大括号包起来）
send('{#000P1500T1000!#001P2000T1000!#002P1200T1000!}')

# 按坐标移动（逆运动学）：x=150 y=120 z=60，用时 1s
send('$KMS:150,120,60,1000')

# 执行第 3 组动作
send('$DGS:3')

注意两件事：① 指令结尾的 ! 由 send() 统一补上，避免漏写；② time.sleep(0.05) 给单片机留出解析时间（因为它是「一条处理完才收下一条」的丢包式流控）。

14.4 联调顺序建议

  1. 只上电、不发指令：听 3 声蜂鸣 + LED 每秒闪 → 说明基础系统正常。串口应能看到 W25Q64 ID=ef16。
  2. 发 $DRS!：应回 hello,world! → 说明串口收发链路通了。
  3. 发 #000P1500T1000!：0 号舵机应缓慢转到中位 → 说明解析 + PWM 链路通了。
  4. 逐个舵机试限位：#000P0510T2000! 和 #000P2490T2000!，看是否撞结构。撞了就改 servo_pwm_min/max。
  5. 校准中位：用 #000PSCK+030! 一点点调，直到爪子正对前方。
  6. 试逆运动学：$KMS:150,120,60,1000!，看爪子尖是否到达预期位置（用尺子量）。
  7. 试手柄：插上手柄，按键看是否响一声 + 舵机动作。
  8. 最后试动作组：存一组、读回、执行。

这个顺序的原则是「从最底层往最上层验证」：每步只增加一个变量，出问题时能立刻定位到是哪一层坏了。反过来（一上来就试动作组）会让你在 6 个环节里瞎猜。

A.2 逆运动学错误码

返回码含义
0成功
-1目标点低于底座（z 太低）
2目标太远，超出臂长（> L1+L2）
3肘关节 acos 参数越界（几何无解）
4肘关节角超出 ±135°
5肩关节异常（目标落在肩上 / acos 参数越界）
6肩关节角超出 0~180°
7腕关节角超出 ±90°

A.4 术语表

术语本项目中的含义
脉宽 / PWM 值 / 位置同一件事：高电平持续的微秒数，如 1500
动作组一组多舵机指令的集合，存在 Flash 里，编号 0~9999
预命令（pre_cmd）上电自动执行的一条命令
偏差（bias）每个舵机的校准补偿值，范围 ±500μs
防猛动上电时先恢复上次位置再平滑归位，避免机械冲击
时隙软件 PWM 里分配给一路舵机的 2500μs 时间片
丢包式流控上一条指令没处理完就丢弃新数据 if (uart1_get_ok) return;
前后台系统中断（前台）+ 主循环（后台），无 RTOS
